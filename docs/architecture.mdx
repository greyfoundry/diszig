title: 'Architecture'

The intended SDK has a thin public client facade and independently usable lower-level modules. Protocol types are shared, REST handles request scheduling and rate limits, and Gateway handles session recovery and event delivery. Builders and interaction helpers should work without requiring a full Gateway client where appropriate.

The intended repository is a Zig monorepo. A future root build will coordinate real packages; new modules are introduced when their functionality exists. The documentation site is a separate toolchain, not a runtime dependency.

The planned SDK layout is:

```text
build.zig / build.zig.zon  Root build and consumer package
src/root.zig              Public entrypoint
packages/protocol/        Shared wire types, IDs, permissions and routes
packages/rest/            HTTP transport, authentication and request scheduling
packages/gateway/         Sessions, recovery and event delivery
packages/builders/        Validated message and interaction payloads
packages/interactions/    Response lifecycle and signed HTTP delivery
packages/client/          Client facade, managers and cache policy
packages/sharding/        Native shards and local worker supervision
packages/voice/           Optional voice integration
examples/                 Compiled consumer examples
tests/                    Cross-package fixtures and failure tests
benchmarks/               Reproducible measurements
```

These paths describe responsibilities, not existing packages. The protocol skeleton exists: `snowflake.zig` provides strict decimal IDs and timestamps, `timestamp.zig` parses and formats ISO8601, `cdn.zig` validates CDN image identity, `permissions.zig` implements documented overwrite ordering, `presence.zig` distinguishes absent/null/value, `errors.zig` provides bounded redacted context and `json.zig` provides tolerant-enum, one-of, size and depth bounds. `packages/protocol/models/shared.zig` begins the reviewed model batches with shared gateway/error/GitHub/automod/enum/permissions wire contracts; `packages/rest/errors.zig` maps HTTP status and nested Discord validation errors without a global last-error, `packages/rest/client.zig` provides a standalone bounded REST transport with credential separation and same-origin redirects, `routes.zig`/`request.zig` provide normalized limiter identities and percent-encoded targets, and `limiter.zig` provides learned buckets, global pauses and bounded admission. `retry.zig` separates safe retries from ambiguous non-idempotent writes with finite attempt and deadline budgets. `multipart.zig` streams uploads, `cdn.zig` builds standard non-signed image URLs, `pagination.zig` provides bounded cursors and `audit.zig` encodes audit reasons. `packages/gateway/transport.zig` opens one WebSocket, reassembles frames, answers pings, surfaces close frames and returns bounded payloads; `compression.zig` decodes Discord's shared `zlib-stream` context with a hard expansion bound; `heartbeat.zig`/`session.zig` parse Hello and drive jittered heartbeats, server heartbeat requests and missing-ACK zombie detection on a background deadline thread; `recovery.zig` builds Identify/Resume payloads, captures Ready state, classifies documented closes and holds separate identify/resume budgets and bounded backoff; `dispatch.zig` and `events/root.zig` provide a fixed-capacity per-shard FIFO with owned copies, typed READY/RESUMED, raw fallback and explicit overload; `protocol/events/channels.zig` and `gateway/events/channels.zig` type the first channel event batch with absent-versus-null updates and unknown-enum retention; `protocol/events/commands.zig` types APPLICATION_COMMAND_PERMISSIONS_UPDATE with a 100-entry bound; `protocol/events/guilds.zig` and `gateway/events/guilds.zig` type the first guild batch with a batch-1 guild subset and raw audit-log changes; `protocol/events/integrations.zig` and `gateway/events/integrations.zig` type the integration batch with a shared minimal user model; `packages/protocol/intents.zig` validates intent bits and privileged status, while `send.zig` builds every documented send payload and enforces the 120-events-per-60-seconds connection budget. The pinned client framing is vendored under `third_party/websocket/` with its provenance and local modifications recorded beside it. REST endpoints, automatic Gateway reconnect orchestration, typed event payloads beyond READY/RESUMED and sharding, the client facade, builders and interactions are not implemented yet. The root package and an external consumer are proven before expanding the tree.

## Serialization policy

Inbound responses are decoded tolerantly: unknown fields are ignored when the caller opts in, unknown enum values are retained through `InboundEnum` and can be recovered or reported, and a missing field, an explicit null and a value are distinct through `Presence`. Outbound requests are strict: they use concrete types and must not silently drop or invent fields. A one-of object must contain exactly one branch, checked before the branch is interpreted. Input byte length and nesting depth are bounded before parsing, and allocator failure unwinds the parse arena.

Public types are written and reviewed manually first. Generation is considered only after repeated measured need, with deterministic local inputs, reviewed overrides and no external reference fetching. A self-recursive model is handled with an explicit depth/size bound rather than recursive allocation.

Protocol types sit at the bottom of the dependency graph. REST, Gateway and builders consume them; interactions and the client compose lower-level modules. Sharding shares Gateway contracts across native and hybrid modes. Optional voice must not become a dependency of a basic REST consumer. Package names and public signatures remain subject to compiler-tested design.

Memory ownership, cancellation, error handling and resource bounds are part of the public contract. We will publish precise signatures and examples once the compiler-tested implementation exists.
