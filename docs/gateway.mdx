---
title: 'Gateway transport'
---

The Gateway transport is the WebSocket boundary only. It opens one connection,
reassembles frames, applies transport compression and returns gateway payloads
in order. It does not identify, heartbeat, resume, dispatch or shard yet; those
are separate packages. Do not describe Diszig as having a Gateway client until
they land.

## Connecting

`diszig.gateway.Connection.connect` takes an explicit `ws://` or `wss://` URL:

```zig
const url = try diszig.gateway.Url.parse("wss://gateway.discord.gg/?v=10&encoding=json");

var connection = try diszig.gateway.Connection.connect(allocator, io, .{
    .url = url,
    .compression = .zlib_stream,
    .max_message_bytes = 16 * 1024 * 1024,
});
defer connection.deinit();
```

The caller owns the query string, so the API version and encoding are explicit.
`compress=zlib-stream` is added by the caller together with
`Options.compression`. `ws` is accepted for local fixtures; production Gateway
URLs are `wss`.

`Options.ca_bundle` is optional. When it is null the vendored client scans the
system trust store and verifies the host name; tests pass a local CA bundle.

## Framing

The client framing is vendored from the pinned
[websocket.zig fork](https://tangled.org/zzstoatzz.io/websocket.zig); see
`third_party/websocket/VENDOR.md` for the exact revision and the local
modifications. Diszig does not implement a second frame parser.

- Fragmented data frames are reassembled before `next` returns.
- Control frames are limited to 125 bytes. Pings are answered transparently and
  never surface to the caller. Pongs are ignored.
- Two frames coalesced into one TCP read still yield two messages.
- A close frame is returned as `Message{ .kind = .close }` with the received
  code and reason.
- A socket that closes mid-frame surfaces an error; `next` never returns a
  partial payload.

`next` blocks until a complete payload or a close/error. Cancel a blocked read by
closing the connection from another owner; the shutdown unblocks the reader.
`Session.connect` bounds the initial Hello wait with a watchdog that closes the
socket at the handshake deadline. A positive `SO_RCVTIMEO` is deliberately not
used: Zig 0.17's Linux `Io` treats `EAGAIN` from a timed-out socket as a
programmer bug before the WebSocket client can map it to a timeout.

## Transport compression

`zlib-stream` is one zlib context per connection, shared by every payload.
Discord terminates each payload with the four-byte `Z_SYNC_FLUSH` marker
`00 00 ff ff`, and the next payload continues the same stream, so
back-references can reach earlier payloads.

Zig's `std.compress.flate.Decompress` cannot be paused between input chunks, so
Diszig links zlib 1.3.2 (pinned in `build.zig.zon`) and uses its incremental
inflate interface. This does not reimplement a codec.

`Options.compression` is explicit:

| Value | Behaviour |
| --- | --- |
| `.none` | No transport compression. |
| `.zlib_stream` | Shared zlib context, bounded expansion. |
| `.zstd_stream` | Documented by Discord, not implemented; returns `error.UnsupportedCompression`. |

`max_message_bytes` bounds both the decompressed payload and the compressed
bytes accumulated between two markers. A compressed expansion over the bound
fails with `error.MessageTooLarge`, poisons the decoder and requires a new
connection.

## Bounds and ownership

- `max_message_bytes` defaults to 16 MiB.
- `read_buffer_bytes` must be less than or equal to `max_message_bytes`. The
  client has a static read buffer, and a larger buffer would let an oversized
  message bypass the message limit.
- `Message.data` is borrowed and valid only until the next `next`, `close` or
  `deinit` call.
- `sendText` copies the payload into a private buffer, because the framing masks
  outbound payloads in place. The copy is wiped after the write. Gateway send
  payloads can contain the Identify token.

## Session control

`diszig.gateway.Session.connect` wraps the transport and requires Hello as the
first payload:

- `parseHello` reads `heartbeat_interval` and rejects a non-positive value.
- The first heartbeat is delayed by `heartbeat_interval * jitter`, where the
  caller may supply a deterministic jitter in [0, 1) or let the session draw a
  random value.
- `parseEnvelope` reads only the top-level `op` and `s`; a large `d` is skipped
  without building a value tree.

Heartbeats follow Discord's documented contract:

- `tick` sends `{"op":1,"d":<last sequence or null>}` when a deadline is due.
- An ACK (op `11`) clears the outstanding heartbeat. A server heartbeat request
  (op `1`) asks the next `tick` to send immediately.
- If the next deadline arrives with no ACK, `tick` returns `.zombie`, the session
  closes with code `4000`, and the caller must reconnect and resume (GW-03).
- A delayed loop sends one heartbeat and reschedules a full interval later; it
  does not emit a burst of missed beats.

`startHeartbeat` runs the scheduler on a separate thread that only writes
heartbeats. The caller's I/O owner keeps calling `next`, which consumes ACKs and
server requests. User handlers must run on worker capacity (GW-04), never on
either path. `stopHeartbeat` joins the thread; `deinit` calls it.

Identify and Resume payloads are validated and built by
`diszig.gateway.recovery.writeIdentify` / `writeResume`. Credentials and
session IDs are restricted to token-safe characters so they cannot inject JSON;
the session wipes its scratch buffer after sending. `sendIdentify` and
`sendResume` never retain the token.

`Session.next` captures a READY payload into `recovery.state` (session ID,
`resume_gateway_url`, last sequence) and a RESUMED payload resets the backoff.
It also updates `recovery` for:

- **Close**: documented 4000-4014 codes are classified. 4004, 4010-4014 are
  fatal and never loop. 4007 and 4009 require a new Identify. Normal 1000/1001
  closures stop. Abnormal loss and unknown 4xxx codes are resumable but bounded.
- **Invalid Session (op 9)**: `d: true` resumes when possible; `d: false` clears
  the session and Identifies.
- **Reconnect (op 7)**: resumes when possible, otherwise Identifies.
- **Transport loss without a close frame**: `onTransportLost` treats it as an
  abnormal, resumable closure.

Identify and resume allowances are separate fixed-window budgets. Identify
defaults to Discord's documented 1000 per 24 hours; the resume budget is a
Diszig loop guard. Backoff is exponential from 1 s to 60 s with a bounded attempt
count. When either budget or the attempt count is exhausted the decision is
`.exhausted`, and the caller stops. The automatic reconnect loop, dispatch and
sharding are not implemented; the caller drives the delay and reconnect.

## Dispatch and backpressure

`diszig.gateway.dispatch.Queue` is a fixed-capacity FIFO for one shard:

- `tryPush` copies the name, sequence and payload; the transport buffer is not
  retained.
- `pop` returns a borrowed event valid until `release` or slot reuse. Call
  `Event.copy` to retain it past the callback.
- A full queue returns `error.QueueFull` and increments `droppedCount`. It never
  grows, blocks the reader or delays a heartbeat.
- One consumer per queue preserves order. Multiple consumers on one queue break
  that guarantee.
- Resume replay can deliver a duplicate. The queue does not deduplicate; use
  `sequence` when a handler must be idempotent.

`Session.nextDetailed` returns the message plus the parsed envelope (name, op,
sequence) so the caller can push a dispatch without re-parsing. Control frames
(heartbeat ACK/request, close, reconnect, invalid session) are handled before
the event is returned; they never wait for application callbacks.

`diszig.gateway.events.decode` types READY, RESUMED, the first channel batch
(CHANNEL_CREATE, CHANNEL_UPDATE, CHANNEL_DELETE, CHANNEL_INFO and
CHANNEL_PINS_UPDATE), APPLICATION_COMMAND_PERMISSIONS_UPDATE, the first guild
batch (GUILD_CREATE, GUILD_UPDATE, GUILD_DELETE, GUILD_AUDIT_LOG_ENTRY_CREATE,
GUILD_BAN_ADD, GUILD_BAN_REMOVE), the integration batch (INTEGRATION_CREATE,
INTEGRATION_UPDATE, INTEGRATION_DELETE), INTERACTION_CREATE, the invite batch
(INVITE_CREATE, INVITE_DELETE), the member batch (GUILD_MEMBER_ADD,
GUILD_MEMBER_UPDATE, GUILD_MEMBER_REMOVE, GUILD_MEMBERS_CHUNK), the message
batch (MESSAGE_CREATE, MESSAGE_UPDATE, MESSAGE_DELETE, MESSAGE_DELETE_BULK) and
the role batch (GUILD_ROLE_CREATE, GUILD_ROLE_UPDATE, GUILD_ROLE_DELETE), the thread batch (THREAD_CREATE, THREAD_UPDATE, THREAD_DELETE, THREAD_LIST_SYNC, THREAD_MEMBER_UPDATE, THREAD_MEMBERS_UPDATE), the reaction batch (MESSAGE_REACTION_ADD, MESSAGE_REACTION_REMOVE, MESSAGE_REACTION_REMOVE_ALL, MESSAGE_REACTION_REMOVE_EMOJI) and the poll vote batch (MESSAGE_POLL_VOTE_ADD, MESSAGE_POLL_VOTE_REMOVE).
Every other event is `.raw` with the original gateway envelope; EVENT-* packages
add typed payloads.

Typed channel payloads use `Presence` for nullable fields: an omitted update
field is absent and does not clear it, while an explicit null is a clear.
Unknown channel and overwrite enum values are retained in `InboundEnum`; unknown
JSON fields are ignored. The batch-1 channel model covers identity and type,
guild, name/topic, position, permission overwrites, pin timestamp, voice limits,
flags and thread counts; MODEL-CHANNELS-* extends the full resource. Typed
slices borrow the per-callback arena.

INTERACTION_CREATE types the envelope: id, application, type, guild/channel,
member or DM user, permissions, locale, context and attachment limit. `token` is
a continuation secret retained only in the callback arena; it must not be logged
or stored. Interaction `data`, `message`, `entitlements` and authorizing owners
are action-specific and remain raw JSON in this batch; MODEL-INTERACTIONS-*
types them.

Member events (GUILD_MEMBER_ADD/UPDATE/REMOVE and GUILD_MEMBERS_CHUNK) use the
shared member model: user, nick/avatar/banner, roles, joined_at, premium_since,
deaf/mute/flags, pending, permissions and timeout. The add/update payloads are
flat member fields plus `guild_id`, which the decoder parses separately. Chunk
presences remain raw for this batch.

Message events share a batch-1 `Message` model. `MESSAGE_UPDATE` is a partial
message: `Presence` fields distinguish an omitted update from an explicit null.
Attachments are typed; embeds, components, reactions, references, polls and
interaction data remain raw. `MESSAGE_DELETE` and `MESSAGE_DELETE_BULK` are
separate typed payloads.

## Send operations and intents

`diszig.intents` mirrors the documented bit table. `validate` rejects
undocumented bits, and `isPrivileged` covers `GUILD_MEMBERS`,
`GUILD_PRESENCES` and `MESSAGE_CONTENT`. `writeIdentify` refuses a privileged
bit unless the caller sets `allow_privileged`, which is an explicit confirmation
that the intent is enabled in the Developer Portal. A server rejection (close
`4013`/`4014`) remains fatal in the recovery policy.

`diszig.gateway.send` builds every documented send payload:

- Identify and Resume (re-exported from `recovery.zig`) and Heartbeat.
- Request Guild Members: exactly one of `query` or `user_ids`; query at most
  100 bytes; limit at most 100 for a prefix and 1000 overall; at most 100 user
  IDs; nonce at most 32 bytes and JSON-safe.
- Request Soundboard Sounds: 1-100 guild IDs.
- Request Channel Info: `status` and/or `voice_start_time`, no duplicates.
- Update Voice State: `channel_id: null` disconnects.
- Update Presence: status, `since`, `afk` and up to 10 activities with escaped
  name/url/state/details text.

Every builder writes into a caller-owned buffer. `Session.sendText` copies the
payload, lets the framing mask the copy and then wipes it.

`SendLimiter` enforces Discord's 120 events per connection per 60 seconds.
Non-critical sends return `error.RateLimited` with `retryAfterMs`; heartbeat,
Identify and Resume are critical and are counted but never blocked. A
`RATE_LIMITED` dispatch is parsed by `send.parseRateLimited` into the offending
opcode, retry delay and metadata (guild ID, nonce). It is deliberately a
different type from an HTTP 429: only the named operation should be postponed,
and there is no HTTP status or global flag.

## Not implemented yet

Automatic reconnect orchestration, typed event payloads beyond READY/RESUMED,
worker pools, sharding and the client facade. None of those are claimed by this
page.
