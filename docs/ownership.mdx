---
title: 'Ownership and concurrency'
---

These are the binding contracts for Diszig implementation. The REST transport and the Gateway framing boundary exist today; the session, client and dispatcher must keep following these rules as they are built. The contracts are written before public signatures so allocator and lifetime mistakes are not frozen into the API.

## Allocators

- There is no global or hidden allocator. Each long-lived owner stores the `std.mem.Allocator` passed to its `init`.
- `init` either returns a fully usable value or fails after releasing every allocation it made. A partially initialized client is never returned.
- Operations that produce caller-controlled data take an allocator and return an owned result. The caller calls that result's `deinit` with the same allocator.
- The client copies any input it must retain beyond the call. It never stores a caller's borrowed slice.
- WebSocket send buffers are not reusable after a send: the selected transport masks the caller's mutable payload in place. Outbound frames are built in a transport-owned scratch buffer or copied first.
- `deinit` is called exactly once, after the owner has stopped and joined its work. It is not safe to call concurrently with other methods.

## Event data

- Gateway dispatch data is decoded into an arena owned by the dispatcher for one callback.
- Slices in the event passed to a callback are borrowed and valid only until the callback returns.
- To keep data, call the event's copy or ownership helper before returning. The copy is independent and has its own cleanup.
- Callbacks must not store pointers into the borrowed event, and must not call `deinit` or stop the client from inside a callback.

## Dispatch and threads

- One I/O owner per shard reads the socket, parses payloads and handles compression. A bounded heartbeat thread writes heartbeats against a monotonic deadline and never runs user code.
- The heartbeat thread is joined before the transport is released. `stopHeartbeat` is idempotent and `deinit` calls it.
- User callbacks run on bounded worker capacity, never on the heartbeat or socket control path. A slow callback therefore cannot delay a heartbeat, an acknowledgement or a close.
- Callbacks for one shard are serialized to preserve dispatch order. Different shards may run callbacks concurrently.
- Dispatch queues are bounded. A full queue returns `error.QueueFull` and increments a dropped counter; it never grows and never blocks the heartbeat. The caller decides whether to log, count or treat the overload as a reason to close.
- No undocumented background service is started. The I/O thread, heartbeat thread and worker pool are created at start and joined during shutdown.
- Shared state uses `std.Io` synchronization primitives. No lock is held while a user callback runs.

## Cancellation and shutdown

Shutdown order is fixed:

1. stop accepting new work;
2. signal cancellation and wake waiters;
3. close the transport;
4. wait a bounded grace period for callbacks;
5. join the owned I/O and worker threads;
6. release resources.

Cancellation uses `std.Io` cancellation and explicit wake events. A handler cannot be safely force-killed. If a handler is still running after the grace period, shutdown returns a timeout error instead of freeing memory that the handler may still reference. The caller may retry shutdown after the handler returns. This preserves memory safety over an unbounded wait.

A blocked Gateway socket read is cancelled by closing the transport from another owner. The shutdown unblocks the read and returns an error; the transport does not use a positive `SO_RCVTIMEO`, because Zig 0.17's Linux `Io` treats the resulting `EAGAIN` as a programmer bug. The initial Hello wait is bounded by a watchdog that closes the socket at the deadline.

## Errors and redaction

- Errors are returned as typed Zig error unions. Diagnostic data is written to a caller-owned `packages/protocol/errors.zig` context; there is no global last error.
- The context records a kind, HTTP status, Discord code, retry delay and bounded detail. It allocates nothing.
- Route text should be a template such as `/webhooks/{}/{}`, not a formatted URL.
- Detail text is capped at 256 bytes and redacts `Authorization` header values, `token=` parameters, bot-token-shaped strings and webhook token path segments.
- Tokens, webhook secrets and raw response bodies are not retained. Callers must not put credentials into a context manually.
- A wrong result is never reported as success. Ambiguous non-idempotent writes have their own error kind and are not retried as if they succeeded.

## Current evidence

Compiled probes on Zig 0.17.1 verify borrowed-event copying, cleanup when the second allocation fails, and a blocked worker that is woken and joined within a bounded timeout. The Gateway transport has a local raw-socket fixture for coalesced frames, fragmentation with an interleaved ping, masked pong replies, a close frame with code and reason, a mid-frame disconnect, two compressed payloads and an expansion bomb. The heartbeat has a fixture where the probe never calls `tick`: the background thread sends heartbeats on the documented cadence, carries the last dispatch sequence, answers a server heartbeat request within one slice, and closes with 4000 when an ACK is withheld. Recovery policy has deterministic tests for resumable loss, invalid-session reidentify, fatal close codes, separate identify/resume budgets and bounded backoff. The dispatch queue has deterministic tests for FIFO copying, full-queue overload with a live heartbeat, duplicate replay and the explicit copy path. The first typed channel event batch has tests for minimal payloads, partial updates versus explicit nulls, absent privileged/thread data, unknown enum retention, raw fallback and allocation-failure cleanup. The application command permissions event has tests for typed values, unknown permission types, the 100-entry bound and allocation-failure cleanup. The first guild batch has tests for full and unavailable guilds, partial updates, raw audit-log changes, ban payloads and allocation-failure cleanup. The automatic reconnect loop and worker pool will add their own cancellation, ordering and shutdown tests before any support claim.
